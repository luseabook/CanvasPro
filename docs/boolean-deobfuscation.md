# 第 166 批·第四层混淆（布尔字面量）清零

> 起点：用户裁决「先不到 0.8.0，先把本项目处理干净，让本项目无任何混淆的源码」。
> 结果：**17,253 处 / 1,044 件**改写完毕，四道独立检查全过，全量回归零真回归。

## 1. 上一批的结论是错的，这是怎么发现的

第 165 批为核实受保护件 `aigenText/uiModule.js` 的版本，把 `b157/port` 的 12 件暂存件
逐一与两版镜像过改名闸门，发现**全部源自 0.7.16 镜像**。追查过程中顺手 grep 了
`!![]`，得到 **17,253 处 / 1,044 件**——前三批去混淆从未提过这个形态。

原因很清楚：**前三批扫的是不同层的东西。**

| 批次 | 扫的层 | 手段 | 为什么漏掉 `!![]` |
|---|---|---|---|
| 改名批 | 标识符 | token流 | `!![]` 里没有标识符 |
| 158b/159/160 | 字面量 | 转义 + 十六进制 | `!![]` 里没有字符串或十六进制 |
| **166（本批）** | **运算符** | **token 流** | — |

`!![]` 是**运算符序列作用于数组字面量**，不在前三批任何一层里。每一批的
「已清零」在自己的层上都成立，合起来是错的。这是本次真正的方法论教训：
**逐层清零不等于整体清零，必须有一份「当前还有哪些形态」的普查清单。**

## 2. 改写依据：语义等价，不是形态相似

`[]` 在 JavaScript 里是 **truthy**，所以：

- `!![]` ≡ `true`
- `![]` ≡ `false`

这是**语言本身**的规定，不靠人工判断。因此改写可以做严格证明，而不是「看着像」。
校验器第3 道检查把原文交给 JS 引擎实跑（`Function('return (!![])')()`），
返回 `true` 才放行—— **不是模式匹配，是引擎裁决**。

## 3. 三个工具

### `tools/deobf-residue-scan.mjs`（普查器）

先量账再动手。10 类形态走 token 流，字符串/模板/注释/regex 里的内容不会被误判：

| 形态 | 改写前 | 改写后 |
|---|---|---|
| `obf-identifier`（`_0x…`） | 0 | 0 |
| `literal-escape` | 88（按规则保留的控制字符） | 88 |
| `hex-literal` | 661（`vendor` 304 + 刻意常量 357） | 661 |
| **`bool-array`（`!![]`/`![]`）** | **26,102 / 1,044 件** | **0** |
| `void-zero` | 2（`vendor` 上游） | 2 |
| `bracket-member`（`obj['x']`） | 212,886 | 212,886 |
| `char-concat`（`'a'+'b'`） | 1,746 | 1,746 |
| `debugger-stmt` | 0 | 0 |

分布：`src` 23,995 / 914 件、`api` 1,416 / 106 件、`electron` 691 / 24 件、**`vendor` 0**。

`hex-literal` 一项本身也有个教训：第一版探测器读 token 流，报告「0 处十六进制」，
而树里明明有几百处——因为 `lex()` 会把数字归一化成 `String(Number(text))`，
`0xff` 进门时已经是 `255`。**探测器坏了，不是树干净了。** 改成读原文才拿到真数。
同类的错误还有「by tree」那两行输出了完全相同的数值（split函数把全部 kind 加起来
冒充单个 kind）。两个假数都靠交叉核对发现，所以普查结果一律用第二种口径复核。

### `tools/deobf-bool.mjs`（改写器）

token 级定位，只改代码位。两条边界规则：

1. `!` 之后的 `[` `]` 必须是**新鲜的数组字面量**，不是下标或成员链的头——
   `![][0]` 是 `!([][0])`，改括号就改了被取反的对象。实测全仓 **0 处**这种形态，
   守卫是安全网。
2. 切出的原文必须匹配 `/^!{1,2}\[\]$/`，否则**抛错拒绝写入**，不产出「看起来对」的结果。

`vendor/` 无条件排除（上游 three.js）。

### `tools/deobf-bool-verify.mjs`（独立校验器）

四道检查，**刻意不复用改写器的判断逻辑**：

1. **段相等**——把原文按跨度切成 N+1 段 + N 个替换，与磁盘上的文件逐字节比对。
2. **token 流坍缩**——每跨度 token 数必须按可预测量减少（双叹号 −3、单叹号 −2）。
3. **引擎求值**——每个跨度原文交给 JS 引擎实跑，必须返回预期的布尔值。
4. **长度核算**——`![]`→`false` 增长 2、`!![]`→`true` 不变，总增长必须精确等于
   `2 × 单叹号跨度数`。

第 1/2/4 道只做两个文件互比，**改错了但一致地错也会通过**；第 3 道才把每个跨度
钉在语言语义上。

## 4. 踩过的四个坑（都写进了注释和测试）

**① 改写器产出过 `!false`。** 词法器的 `token.offset` 语义是「已推进到 token 之后」，
不是「token 起始」——因为 `i += punctuator.length` 写在 `push()` **之前**。用它当切片
边界时，`return ![]` 被改成 `return !false`：语义相同（都是 `true`），但这正是本批要
消除的可读性垃圾，1 个样本文件里就出现 93 处。**所有只断言行为的测试都会放过它。**
修法：以 `]` 的 offset 为锚点，按已知长度（3 或 4）向前量，并在写入前断言切出的
文本确实匹配 `!{1,2}\[\]`。

没有改词法器：四道既有闸门都读它，改动会波及全部历史结论的复现基础。

**② 校验器用原文偏移去索引新文件。** `![]`→`false` 增长 2 字节，后续跨度全部平移。
首版报 588 条假失败。

**③ 按顺序配对第 N 个替换。** 源码里本来就有真 `true`/`false`——样本文件有 **13 处**，
改写后关键字总数变成 201。计数法在第二个真`false` 之后就永久漂移。

**④ 用跨度前24 字符做锚点。** `indexOf` 找到的是*某个*匹配，不是*下一个*，
重复文本会把跨度配到后面跨度的位置上。

最终解法是**不搜索**：直接从原文跨度和期望替换构造出应有的完整文本，与磁盘比对。
没有定位步骤，就没有可漂移的东西。

**⑤ 导入即执行。** 两个工具的 CLI 顶层在 `import` 时会跑。批量驱动 import 之后，
改写器把驱动的三个路径参数当成目录遍历，**打印出 202,694 处的假数**；
校验器因参数个数为奇数 `process.exit(2)`，主循环一次都没跑。
按仓库既有惯例（`deobf-unescape.mjs` 的写法）加 `process.argv[1].endsWith(...)` 守卫。

## 6. 全量回归 30 例的判读

基线是 **11165/ 27**，本轮 30，看起来净增 3 例。逐条查证后：**真回归 0**。

净增的 3 例是 `electron/installerSafety.test.js` 的：

- `cleanup removes only unchanged manifest-owned program files and keeps data in place`
- `legacy installs without a manifest are not recursively cleaned`
- `unsafe manifest entries abort before deleting any program file`

证据链：

1. **该文件未被本批改动一个字节**——`git status` 干净，且它本来就不含 `!![]`，
   从未进入改写清单。
2. **失败信息是 `null !== 0`**——它测的是 `build/uninstall-program-files.ps1`，
   通过 `spawnSync` 调外部进程。`status: null` 表示**子进程根本没启动**，
   与断言逻辑无关。
3. **它是基线失败，不是本批新增**——第 163 批台账原文写着「基线 3 例
   `installerSafety` 本轮在全量里**全过**」。也就是说这 3 例一直在基线里，
   上一轮只是碰巧全过。

第2条与本机环境事实吻合：沙箱禁止从 Node/Bash 调起 PowerShell，会返回 `null` status。

## 8. 还剩什么（不在本批范围）

普查器量出的其余形态，**都不是混淆残留**，列在这里以免日后重查：

- **`bracket-member` 212,886 处 / 1,991 件**（`obj['prop']`）——移植件的行文风格。
  不是混淆，且**不能机械改写**：`obj['default']`、`obj['class']` 等合法标识符
  必须保留方括号，转换需要逐个判断合法性 + 优先级，属独立课题。
- **`char-concat` 1,746 处**（`'a' + 'b'`）——样本显示是 `':'` 之类的分隔符拼接，
  是正常写法。
- **`hex-literal` 661 处**——`vendor` 上游 304 + 项目刻意常量 357
  （`0xff`、`0x811c9dc5`、`0x7fffffff`、零填充等），已在160 批判定过。
- **`literal-escape` 88 处**——`\x00` / `\xa0` 等控制字符与不可见分隔符，
  按 158b 规则**保留转义**。
- **`void-zero` 2 处**——`vendor/three/examples/jsm/libs/fflate.module.js`，上游正常代码。
