# 单仓工作流

本文说明如何**像管理单仓一样**管理两个**独立 git 仓库**：

- `F:\CanvasPro` —— 客户端（Electron 桌面端）
- `F:\canvas-admin` —— 服务端（授权/CDKEY 服务 + 管理后台）

> 前提：本方案**不物理合并**两个仓库，**不改变**它们各自的独立构建与独立部署。
> 两个仓库仍是独立的 `.git`、独立的分支、独立的 CI/发布流程；这里只做
> 「契约对齐 + 单仓视图 + 统一运维手册」，让维护者在一个视角下工作。

---

## 1. 一条命令总览（推荐入口）

```bash
cd F:\CanvasPro
node tools/canvas-workspace.mjs status
```

输出包含：

- 两个仓库的根路径、当前分支、`git status --porcelain` 的改动条数、最近一条
  commit 的短 hash + 标题；
- 两侧的**契约版本**：从 `F:\canvas-admin\backend\app\services\client_config_service.py`
  抽取 `CONTRACT_VERSION = "..."`，从 `F:\CanvasPro\backend\services\subscription_client.py`
  抽取 `SUPPORTED_CONTRACT_VERSIONS = (...)`；
- **漂移检测结论**：一致打印 `✅ 契约版本一致`；不一致打印 `❌ 契约版本漂移`
  并以**非 0 退出码**结束。

退出码约定：

| 退出码 | 含义 |
| --- | --- |
| 0 | 两侧契约版本一致 |
| 1 | 契约版本漂移 |
| 2 | 无法运行（仓库缺失 / 不是 git 工作树 / 契约版本读不到） |

工具是**只读**的：不写入任何文件，只执行 `git` 只读命令。

### 环境变量覆盖

默认根路径为 `F:\CanvasPro` 与 `F:\canvas-admin`。若仓库不在默认位置：

```bash
CANVASPRO_ROOT=D:\repos\CanvasPro CANVAS_ADMIN_ROOT=D:\repos\canvas-admin \
  node tools/canvas-workspace.mjs status
```

（Windows PowerShell 下等价写法：`$env:CANVASPRO_ROOT="D:\repos\CanvasPro"`。）

## 2. IDE 多根工作区（推荐日常开发方式）

用一个 `.code-workspace` 文件把两个文件夹收进同一个窗口，代码搜索、文件树、Git
面板都能同时看到两边。

### 模板内容

把你常用的编辑器工作区文件（例如 `F:\canvas-workspace.code-workspace`）写成：

```json
{
  "folders": [
    { "name": "CanvasPro（客户端）", "path": "F:\\CanvasPro" },
    { "name": "canvas-admin（后台）", "path": "F:\\canvas-admin" }
  ],
  "settings": {}
}
```

打开方式：编辑器 → 文件 → 打开工作区 → 选中该 `.code-workspace`。此后一个窗口
即可同时浏览/搜索/提交两个仓库。

### 为什么不建议把它提交进仓库

- 该文件包含**开发者本机的绝对路径**（`F:\...`），提交后对其他机器无意义；
- 它会同时“拥有”两个仓库，放进任一仓库都对另一仓库是越界引用，容易造成
  “改一处却提交到错仓库”的困惑；
- 它属于**个人 IDE 偏好**，不是项目的构建/运行时依赖。

因此把它放在**两个仓库之外的任意位置**（如用户目录），按需本地打开即可；
若确实要共享，另建一个不含路径的个人配置仓库，不要塞进 `CanvasPro` 或
`canvas-admin`。

## 3. git submodule 只读聚合仓（可选进阶）

如果希望在同一个目录下用 `git` 同时看到两个仓库（例如给脚本提供统一工作目录），
可以建立一个**只读聚合仓**，把两个仓库作为 submodule 挂入。

### 完整命令序列

```bash
# 1) 在**两个仓库之外**新建聚合仓（切勿建在 CanvasPro / canvas-admin 目录内部）
mkdir F:\CanvasWorkspace
cd F:\CanvasWorkspace
git init

# 2) 以真实远端 URL 挂入两个 submodule
git submodule add https://github.com/luseaer-ship-it/CanvasPro.git CanvasPro
git submodule add https://github.com/luseaer-ship-it/canvas-admin.git canvas-admin

git commit -m "chore: add CanvasPro and canvas-admin as read-only submodules"
```

> ⚠️ **重要警告：不要把 canvas-admin 塞进 CanvasPro 目录内。**
>
> `F:\canvas-admin\backend\tests\test_canvaspro_contract.py`（文件顶部的 `CANVASPRO`
> 常量定义处）有一行：
>
> ```python
> CANVASPRO = Path(__file__).resolve().parents[3] / "CanvasPro"
> ```
>
> 它假设 CanvasPro 是 canvas-admin 的**兄弟目录**（`parents[3]` 从
> `.../canvas-admin/backend/tests/` 上溯到盘根，再拼 `CanvasPro`）。一旦目录结构
> 变成 `.../CanvasPro/canvas-admin/...`，该路径会指向不存在的
> `.../CanvasPro/CanvasPro`，契约测试会**静默 `pytest.skip`**——测试显示“跳过”
> 而非“失败”，形同失效。因此 submodule 聚合仓必须建在两个仓库**之外**，
> 保持二者的兄弟关系。

### 维护

```bash
# 拉取两个 submodule 的最新提交（只读同步）
cd F:\CanvasWorkspace
git submodule update --remote --merge
```

聚合仓本身只用来“看”，日常改动仍在各自子仓库内进行、各自提交。

---

## 4. 边界（务必牢记）

- 本工作流**不改变**两个仓库的独立构建与独立部署：客户端仍走 electron-builder
  出包 + GitHub Releases，后台仍走 Docker Compose 独立上线。
- 两个仓库**各自提交、各自发布**；聚合仓 / 工作区只是**视图**，不是新的事实来源。
- 契约一致性以 `node tools/canvas-workspace.mjs status` 与两侧契约测试为准
  （见 `docs/operations-runbook.md` 的「契约变更流程」）。
