# 第十三批：有限串行镜头媒体生成

在第12批镜头来源/本地采纳链路上接入真正的原媒体生成入口，不另建厂商API。**本批源码已落地；测试、应用、真实生成与保存重开均未运行验收。** 总目标仍是R01–R26，不是只做工作室。

> 第19批复用同一runner和runtime的受限来源适配接入人物/场景资料图片批次，见 `story-asset-media.md`。资料用独立asset来源身份，不伪造episode/shot ID；仍只明确的名称/设定文字，不带已有参考图；沿用原held/attempted和图片缺taskId防自动重提。以下描述保留第13批镜头默认语义，新资料入口不会自动扩展镜头批次的媒体输入。

## 用户操作

1. 工作室 → 选择单集 → **镜头媒体**。勾选本集1–6镜，分页保留选择，换单集清空；执行顺序以当前镜头顺序为准，不以点击顺序为准。
2. 选择图片或视频模型，点 **已选镜头 → 图片/视频批次（先建节点）**。确认应用所有草稿后，批量建立标准AI节点，尚未请求生成。各镜同类已有节点达到6个则拒绝整批；重建会创建新节点，不能当作厂商去重。
3. 在批次页点 **准备原节点（不提交生成）**，挂载、固定本批节点，核对公开 `runGeneration/getGenerationStatus`。可查看各项文字、模型与常用已存参数；未列参数沿用原模型默认，**不是完整API请求预览或报价**。本批新节点不复制其他节点配置，不连接参考媒体。
4. 点 **确认费用并开始 / 继续未发送项**，再确认可能分别计费。逐项 await 原 `runGeneration({})`，只有确认本次成功结束并得到本地原媒体，才自动进入下一项。
5. 失败、异常、没有观察到本次结束、部分失败、远程/缺本地原媒体都会暂停。原节点仍显示运行中时拒绝继续。同一项不自动重试、不自动换模型；用户可再次确认，继续其余未发送项。
6. **暂停后续（不取消当前）** 或返回工作室，不再调用后续项。已经调用的原任务仍可能执行/计费，不把UI暂停当作厂商取消。
7. 回镜头媒体页刷新，按第12批方式查看实际结果、逐项**采纳并应用**，最后使用**原工程保存**。结果不自动关联、不自动渲染成片。

本批只做“纯镜头文字 + 原模型默认”的有限图片/视频生成，暂不编排参考图、首尾帧、人物/场景批量素材。要在原节点人工调整提示词/连线/媒体输入，可使用原单镜入口；批次对这类变化保守阻止，不悄悄把额外素材送出。

## 契约与执行保护

- `prepareStoryMediaBatch` 先构造全部节点并验证上限、模型、提示词与安全落点；`applyStoryWorkspaceDraft` 在任何写入之前校验草稿、来源版本、所有节点ID和批次标记。1–6节点共用一个history commit，不逐个提交半批预期失败。原store/commit抛错仍非跨存储原子事务，不宣称回滚。
- 复用 `nodeRuntimeRegistry` 与 renderer `pinNode/flushNodes/unpinNode`，不调用私有 `_onGenerate`、不伪造HTTP请求、不克隆API Key/URL/媒体参数为请求载荷。传给公开执行入口的options只有 `{}`；实际鉴权、参数构建、厂商调用、结果落地和已知taskId查询仍走原组件。
- 准备时最多40次挂载尝试，默认间隔50ms，另等一次默认控件稳定；不是严格墙钟2秒保证。超限或公开方法缺失即拒绝，不偷偷调用私有方法兜底。所有退出路径释放pin；关闭时若原run Promise仍未结算，延迟释放到结算，避免把关闭冒充已终止。
- 同一页面本模块一次只等待一个批次入口执行；不覆盖原单镜按钮、其他浏览器/页面、厂商后台并行任务。公开入口若提前返回但原状态仍忙，判待核对并暂停，不自动进入下一个。
- 发送前及每项分别重查nodes对象身份、源工作室baseSignature、稳定镜头ID/提示词、模型可用性、无新增入边/引用、原runtime身份/空闲状态及节点参数比较记录。参数比较值只驻内存、最多256Ki字符/节点，不写入节点/日志/快照，不作为请求发送；位置/尺寸/显示名变化不算请求变化。
- 原图片/视频节点可能进行异步默认参数初始化；准备后再变动会保守阻止。需回原节点核对或重新建立批次，不自动调整为其他参数。
- 每个新节点带 `storyMediaBatch:{version:1,batchId,state:'held'}`；调用前写成 `attempted` 并commit画布历史。此标记是**保守的本地尝试边界**：原节点可能因无密钥/校验/预览模式而未真正提交；标记与逻辑调用次数都不是厂商账单次数。
- 标记/commit失败，绝不调用这一项的原生成入口。进入调用后异常一律待核对，不从错误对象导出可能含凭据的原始响应，不自动重发。一次批次入口调用里原厂商客户端已有的查询或HTTP重试不等于一次账单，本批不宣称网络侧幂等。
- 成功判定必须有原流程真实写入的 `generationStartTime > 0`、不在生成、jobStatus success及全为可采纳的本地原媒体结果；此判定仍不证明文件存在/内容正确。部分成功保留在原节点供人工采纳，暂停后续，不丢弃已付费结果。

## 恢复与保存的真实边界

- 本批不新建持久化媒体队列、不读写第7–9批文字队列数据库、不默认开启自动保存。批次窗口的准备/进度只在当前会话；关闭/刷新不会重建并自动启动批次。
- held/attempted标记、原taskId/status和结果都在画布节点，复用原serializer；只有原工程保存成功后才能依赖磁盘副本。**history commit不是磁盘保存成功回执。** 未保存、撤销、清理缓存/媒体、异常退出都可能使记录或文件不可用，不能承诺跨刷新防重复计费。
- 保存重开后，未发送节点可在原入口人工处理，已尝试节点需要核对原状态/厂商记录；本批没有将恢复记录重新排队的入口。不能把文字队列的3次尝试、8MiB快照和自动保存检查点混用为媒体恢复保证；原文字队列规则完全未改。
- 审计发现原图片组件在APIMart/PPIO异步任务没有taskId时存在自动fallback重新生成。为避免本批恢复绕过确认，仅在 `_shouldFallbackRegenerateAsyncTask` 对 `storyMediaBatch.version===1`（入参或当前store）拒绝这条自动重提。普通未标记节点仍按原逻辑，人工 `runGeneration` 不被禁止；有taskId的原查询路径不受影响。不是取消已有厂商任务，也不是全局改写原生成策略。
- 新建节点本来无任务/结果；准备阶段拒绝历史任务标识、时间戳、忙状态或已有结果。模型缺失不影响第12批已有结果的读取/采纳。

## 同步修复的第12批问题

原生命周期实际写入 `generationStartTime`，不是第12批选择标记使用的 `generationStartedAt`。本批优先读真实字段并兼容旧别名；即使原输出路径相同，新的生成开始时间也使旧结果选择失效。已采纳源节点的文件字节仍不受保护，外部同路径覆盖不在此修复范围。
